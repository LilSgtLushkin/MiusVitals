# Папки версий

Каждая папка — полный исходник, из которого собран установщик с этим номером: `src`, `tests`,
`tools`, `fixtures`, `build.bat`, `run_tests.bat` и проекты Visual Studio 2026. Этого достаточно,
чтобы открыть папку в VS 2026 и отлаживать ровно то, что стоит у игроков.

| папка | что это |
| --- | --- |
| `1.0.7/` | бэкап: исходник установщика 1.0.7, больше не меняется |
| `1.0.8/` | рабочая: правки для 1.0.8 вносятся здесь |

## Как работаем каждой версией

1. Новая версия — копия предыдущей папки. Правки вносятся в копию, прошлая папка остаётся бэкапом.
2. Из исправленной папки собирается установщик.
3. Вышла следующая версия — позапрошлую папку удаляем. Создали 1.0.9 → удалили 1.0.7, 1.0.8 осталась
   бэкапом. Дольше двух версий в `development/` не живёт: самый старый архив — 1.0.0 в корне.

## Что править при выпуске новой версии

1. Скопировать прошлую папку: `1.0.9` из `1.0.8`, правки вносить в копию.
2. `current.txt` — поставить новую версию.
3. `env: VERSION:` в `.github/workflows/{build-network-module,publish-installer,verify,render-cache-smoke}.yml`.
4. Пути в `.vscode/{tasks,launch,settings,c_cpp_properties}.json` (VS Code не читает `current.txt`).
5. Удалить позапрошлую папку версии и позапрошлый установочный архив.

`.gitattributes` и `.gitignore` правятся один раз: там маски `development/versions/*/…`.

## Как установщик попадает в main

Порядок не очевиден, и его легко нарушить:

1. Гейт (`build-network-module.yml`) запускается **только на pull request** и вручную; на push в
   `main` он не запускается. Слияние PR гейт не запускает.
2. `publish-installer.yml` ждёт успешного гейта (`workflow_run`) и выполняется **из копии файла на
   `main`**, а не из ветки: версию и пути берёт оттуда, а исходник — из коммита, который гейт
   проверил.
3. Готовый архив он коммитит в **ветку PR** (`workflow_run.head_branch`), и в `main` тот попадает
   вместе с самим PR.

Отсюда правило выпуска: сначала вливается PR с исходником новой версии, затем открывается
следующий PR (любой — например правка документации): его зелёный гейт и есть команда «собери и
опубликуй установщик текущей версии». Пока обновлённый `publish-installer.yml` не попал в `main`,
публикатор из старой копии перезапишет архив **прежней** версии сборкой из нового исходника —
ровно это и произошло один раз: сборка 1.0.8 легла в архив 1.0.7.
