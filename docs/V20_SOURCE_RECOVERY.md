# Восстановление исходника v20: что возможно, что сделано, как продолжаем

Дата: **2026-10-26**. Ветка `arena/97cfb6a3-miusvitals`.

Задача: получить **свой** сетевой код, который можно править, не теряя то, ради чего игроки ставят
мод, — синхронизацию боя, подключение по Steam, UPnP и по IP.

Короткий ответ: **собрать побайтово-идентичный исходник v20 невозможно** (нет ни одного файла
исходника, потеряны имена локальных переменных, шаблоны STL, точные типы). **Собрать
функционально эквивалентный исходник — можно**, и это перестало быть гаданием: у нас есть
именованный разбор всех 895 функций и рабочая декомпиляция. Ниже — числа, метод и план.

## 1. Главный результат: у v20 появился именованный разбор

v20 разобран по `.pdata` (точные границы функций, без эвристик) и сопоставлен с публичным
исходником v12 по структуре кода. Сопоставление идёт не по адресам, а по **профилю инструкций,
потоку управления и ссылкам на строки**, потому что v12 и v20 собраны разными версиями MSVC:
регистры, смещения кадра и адреса там не совпадают, а структура кода — совпадает.

| Статус | Функций | Байт кода | Что это значит для порта |
|---|---|---|---|
| **SAME** | 572 | 114 123 | код структурно совпадает с v12 → **исходник уже есть в публичном дереве** |
| **CHANGED** | 105 | 32 763 | функция v12 с правками → берём v12 и вносим дельту |
| **NEW** | 218 | 116 356 | функций в публичном исходнике нет |
| **всего** | **895** | **263 242** | |

Но 218 NEW — это не 218 задач. Часть «новых» функций появилась не потому, что кто-то написал
код, а потому что **компилятор другой версии заново создал инстанцирования STL и служебные
thunk'и**. Разделение по природе кода:

| Что это | Функций | Байт | Работа |
|---|---|---|---|
| **NEW:logic** | 143 | 80 531 | писать по декомпиляции |
| **NEW:unknown** | 36 | 26 562 | сначала прочитать псевдо-C и назвать, потом писать |
| NEW:stl | 35 | 8 866 | инстанцирования шаблонов: **вернутся сами** при сборке |
| NEW:plumbing | 4 | 397 | статические инициализаторы и `atexit`-thunk'и: тоже код компилятора |

Итог: писать руками нужно **284 функции** (105 CHANGED + 143 logic + 36 unknown), из них 86
мельче 128 байт — это одно-двухстрочные расхождения, их видно диффом, а не проектированием.

Полный список: [`reports/v20-functions.csv`](../development/v20-recovery/reports/v20-functions.csv),
разбитый на этапы и снятый с учёта — [`reports/v20-backlog.md`](../development/v20-recovery/reports/v20-backlog.md):

| Этап | Что | Функций | Байт |

| M4 | лобби и силы | 29 | 30 004 |

### Почему разбор стал возможен

Найдено то, чего не было ни в одном прежнем разборе: в публичном репозитории лежат **MSVC
объектные файлы** (`_mp_research/basic_network/build/*.obj`) со **полной таблицей символов** и
`/Gy`-секциями (одна функция — одна секция). Это даёт v12 с настоящими C++-именами
(`?session_frame@@YAXPEAUObjMan@@@Z`, `?merge_moves@opsave@@YAI…`), а не с `sub_0040DEAD`.

`v20tool.py names` переносит эти имена на бинарник v12: **519 из 602** функций получили имя
автоматически, остальные 83 — это код, которого нет в объектных файлах (внутренние помощники
компилятора и небольшое расхождение между снимком `build/` и релизным v12).

## 3. Декомпиляция работает

Ghidra в этой среде недоступна (релизные архивы GitHub редиректят на заблокированный хост),
JDK нет. Использован **angr** (PyPI): его декомпилятор на `/O1`-коде MSVC даёт структурированный
псевдо-C со **точными строками** и восстановленными ветвлениями.

Пример — `steam_init` (0x3F75C), дословный фрагмент вывода после `tools/polish.py` (строки
подставлены вместо адресов, имена — из таблицы символов v12):

```c
if (GetEnvironmentVariableA("MP_STEAM", &v2, 32) && !atoi(&v2)) {
    mp_log("steam: switched off (MP_STEAM=0)");
} else if (GetEnvironmentVariableA("MP_STEAM_FAKE", &v2, 32) && _strtoui64(&v2, 0, 10)) {
    g_5df68 = _strtoui64(&v2, 0, 10);
    if ((char)fake_steam_open("MP_STEAM_FAKE", 0, 0)) {
        $sprintf_s@$0EA(g_5dea0, "fake%llu", g_5df68);
        mp_log("steam: TEST STAND-IN for Steam: this game is 'steam:%llu', ...", g_5df68);
    }
} else {
    v6 = GetModuleHandleA("steam_api64.dll");
    if (!v6) mp_log("steam: the game has not loaded Steam's library - no Steam joining");
    if (!(char)steam_bind_interfaces(v6)) return ...;
    g_5de68 = g_5ddc0();      /* SteamAPI_SteamFriends_v017   */
    g_5de70 = g_5ddc8();      /* SteamAPI_SteamUser_v021     */
    g_5de78 = g_5ddd0();      /* SteamAPI_SteamNetworking_v006 */
    ...
    mp_log("steam: ready - user %llu (%s), application %u, %d friends, logged on: %s", ...);
}
```

Этого достаточно, чтобы перенести функцию в C++ с сохранением поведения: видно, какие функции
Steam вызываются, в каком порядке, какие строки и в каких условиях пишутся.

Состояние дампа: **866 функций** разобраны в псевдо-C, **29** — те, где angr не справился
(STL-внутренности и несколько мелких хелперов), выведены списком дизассемблера с подписями строк
и импортов (например `call ole32.dll!CoCreateInstance`), то есть читаются тоже. Полный дамп —
`work/decomp/` (895 файлов), в репозиторий кладётся выборка `reports/decomp/` (155 файлов),
см. §8.

## 4. Стратегия порта: не «переписать всё», а «дерево + дельта»

Ключевое решение. Мы **не** пишем 895 функций с нуля. Мы берём то, что уже есть:

```
публичное дерево (v12, 602 функции)   ← оно компилируется, у него есть IP-подключение,
        │                                UPnP, тактическая синхронизация, экономика, лобби
        │  + 105 правок (CHANGED)
        │  + 218 новых функций (NEW)
        ▼
наше дерево v20-совместимого модуля
```

Причины, почему это правильнее, чем «декомпилировать всё v20»:

1. **v12 — это тот же код в основе.** HELLO, таймаут 8 000 мс, `k_delay 0.10`, `k_run_on 0.25`,
   `MP_APPLY_DELAY 12000`, UPnP, statesync, shots, trench — всё это уже там, на настоящем C++ с
   настоящими именами, а не на восстановленном псевдокоде.
2. **Сеть совместима по формату.** `k_version` и раскладка пакетов в v12/v20 сохраняются; наши
   правки не меняют протокол, поэтому совместимость с текущими сборками не теряется.
3. **Дельта измерима.** 379 строк и 218 новых функций — это список задач, а не «весь мод».
4. **Есть замкнутый цикл проверки** (см. §5) — это главное.

## 5. Замкнутый цикл проверки: MSVC в CI

Раньше считалось, что проверить пересборку нечем. Это не так: в репозитории уже есть workflow
на `windows-2022`, который вызывает `cl /LD /MD /O1 /EHa`. Значит:

1. дерево собирается **тем же компилятором**, что у автора;
2. для SAME-функций можно добиться **побайтового** совпадения с v20;
3. для CHANGED/NEW — сравнение по канонизированному потоку инструкций (`v20tool.py`), которое
   уже работает и даёт объективную метрику «насколько мы близки».

Цикл: правим C++ → собираем в CI → сравниваем каждую функцию с v20 → смотрим расхождения →
правим. Это превращает «декомпиляцию» в обычную инженерную задачу с тестами.

## 6a. M1 и M2: что собрано и что показало сравнение

Дерево `development/net-v21/` — наш собственный модуль. Опубликованный исходник скопирован в
`src/` (манифест SHA-256 фиксирует, что копия не тронута), всё новое написано рядом. `main` и
`development/upstream/` не менялись: это замороженный бэкап. Собирает и сравнивает всё CI
(`.github/workflows/build-network-module.yml`), MSVC 14.44.35207 на `windows-2022`.

### M1 — сборка опубликованного дерева

Те же ключи, что в авторском `build.bat` (`/LD /MD /O1 /EHa /W3`), те же 8 файлов.

| | наш базлайн | релизный v12 |
|---|---|---|
| функций | **602** | 602 |
| байт кода | **156 379** | 156 379 |

Набор функций и их размеры совпали **один в один**. Поструктурное сравнение
(`tools/compare.py`, порог SAME 0.92 + совпадение размера ±2 %):

| статус | функций | байт |
|---|---|---|
| SAME | 380 | 58 299 |
| CHANGED | 192 | 85 434 |
| не сопоставлены | 30 | 12 646 |

Это не разница в исходнике — исходник байт в байт тот же. Это разница **версии компилятора**:
у автора сборка сделана более старым toolset, у нас 14.44, и он иначе распределяет регистры,
по-другому инлайнит и иначе кладёт вызовы. Отсюда два вывода:

1. базлайн годится как отправная точка, сборка воспроизводится;
2. побайтовая сверка с v20 возможна только там, где совпадает ещё и компилятор, поэтому
   рабочая метрика — «структурно то же + живой прогон», а не `fc /b`.

### M2 — Steam-слой

Написан с нуля по спецификации [`V20_STEAM_LAYER.md`](V20_STEAM_LAYER.md): `src/steam.cpp`
(21 слот `GetProcAddress` — ровно те же имена, что в v20; 4 callback'а; P2P; presence с проверкой
чтением; разбор `+gtmf_join=`; стенд `MP_STEAM_FAKE`), `src/steam_module.cpp` (прослойка к
`mp_log` и якорь, который не даёт линкеру выбросить слой), `src/steam_selftest.cpp` (21 проверка).

| | наш модуль | v20 |
|---|---|---|
| функций | **634** | 895 |
| байт кода | **160 871** | 263 242 |

| статус | функций | байт |
|---|---|---|
| SAME | 354 | 50 135 |
| CHANGED | 181 | 57 675 |
| NEW | 99 | ~53 000 |

Близость к v20 по всем функциям: 243 совпадают точно (1.00), 120 ≥ 0.90, 59 ≥ 0.75,
113 ≥ 0.55, 99 < 0.55. То есть **две трети кода уже на месте**, и это не «похоже», а
побайтово.

Осторожно с чтением этих чисел:

* 99 «NEW» — это не «неизвестный код». Сюда попали и наши собственные Steam-функции: они
  написаны заново и по инструкциям не обязаны совпадать с v20. Сравнение показывает «там ли
  мы», а приёмка слоя — по строкам лога и живому прогону.
* Число SAME почти не изменилось между M1 и M2 (354 против 380) не потому, что что-то
  сломалось: M1 сравнивался с v12, где наш базлайн — тот же исходник, а M2 сравнивается с v20,
  где у нас 40 % кода ещё нет. Матчер штрафует за разницу в размере функции, а недостающая
  дельта делает функции систематически короче.
* Разница 634 против 895 — это и есть оставшаяся работа: **261 функция, ~102 КБ**.

### Что нашлось по дороге (и было исправлено)

* Steam-слой сначала **исчезал из образа**: `/O1` включает `/Gy`, каждая функция — свой COMDAT,
  а `/OPT:REF` выбрасывает недостижимое. Ничего ещё не вызывает слой, поэтому линкер честно
  удалял его целиком, и «M2» на самом деле сравнивал базлайн. Поймано по тому, что число
  функций и байт не изменились после добавления файла. Лечение — экспортируемая таблица
  `gtmf_steam_layer[]`: на неё ссылается загрузчик, поэтому весь слой остаётся в образе, а
  `dumpbin /exports` теперь показывает, есть ли слой в конкретной сборке.
* Присутствие в Steam у v20 — **два ключа**, а не один: `gtmf` = `"<номер операции> game"` и
  `connect` = `"root\programs\opgame.progpack, +gtmf_join=steam:<id>"`. Второй Steam
  превращает в пункт «Join Game» у друга; без него друг игру видит, а войти не может. Добавлено
  `steam_broadcast()`, оба ключа проверяются самотестом.

### Что это меняет в плане

1. M1 закрыт: дерево собирается, набор функций совпадает, расхождения объяснены и измерены.
2. M2 закрыт в проверяемой части: слой написан, **реально лежит в образе**, самотест 21/21.
3. Осталась дельта — 261 функция / ~102 КБ против v20, разложенная по этапам M3–M5
   ([`../development/v20-recovery/reports/v20-backlog.md`](../development/v20-recovery/reports/v20-backlog.md)).
4. Перед M3 надо решить: гоняться за побайтовым совпадением с v20 (нужен авторский toolset) или
   принять «структурно то же + живой прогон». Второе дешевле и для правок мода достаточно —
   но тогда и критерий приёмки надо формулировать по поведению, а не по similarity.

## 7. Чего восстановление не даёт

| Потеряно | Следствие | Обход |
|---|---|---|
| Имена локальных переменных и точные типы | псевдо-C читается тяжелее | рядом лежит v12-исходник той же функции — стиль и типы берём оттуда |
| STL-контейнеры в первозданном виде (`std::map`, `std::vector`) | в декомпиляции видны как сырые структуры | формат `.opsave` известен из `opsave.h` (он в публичном дереве) |
| Точные константы (тайминги, пороги) | часть чисел видна в коде, часть выводится из поведения | измерять на живой паре и фиксировать в тестах |
| Побайтовая идентичность | наш модуль не совпадёт по хешу с v20 | и не нужно: нужна совместимость по протоколу |

Отдельно: **совместимость с v20 по сети сохраняется только если не менять `k_version` и раскладку
пакетов.** Это записано как инвариант порта.
