## 2. Механика падения

Аварийная инструкция — внутри функции **`basic_render.codelib + 0x13120…+0x1320A`**:

```asm
00013120  mov [rsp+0x10], rbp ; mov [rsp+0x18], rsi ; push rdi ; sub rsp,0x20
00013135  cmp  edx, -1
0001313a  mov  r10d, edx
0001313d  mov  eax, edx
0001313f  shr  r10d, 0xa                        ; блок = handle >> 10
00013147  add  r10, qword ptr [rcx + 0x240]     ; таблица блоков пула: + (handle>>10)*0x40
0001314e  and  eax, 0x3ff                       ; индекс внутри блока
0001317b  lea  ebp, [rax + rax*4]
0001317e  shl  ebp, 6                           ; *0x140 — размер элемента
00013181  add  rbp, qword ptr [r10]             ; элемент = block->data + idx*0x140
00013184  cmp  dword ptr [rbp + 0x24], r9d      ; ← ПАДЕНИЕ: чтение поля «поколение»
00013188  ja   0x131c1                          ; промах → пересборка (jmp 0x13670)
0001318a  … mov rax,[rcx]; call [rax+0xf8] …    ; попадание → скопировать матрицу 4x4 (0x40 байт)
```

Раскладка пула (видна по всему модулю):

* `[rcx + 0x240]` — таблица блоков, запись **0x40 байт**, первое поле — указатель на данные;
* элемент — **0x140 байт**: `+0x20`, `+0x24` (поколение), `+0x28`, `+0x2c`, `+0x30`, `+0x34`, `+0x38` (слот/флаги), `+0x54`…;
* `[rcx + 0x168]` — пул матриц, запись **0x40 байт** (4x4 float), индекс `слот & 0xFFFFFF`;
* функция `+0x13AB0` — «разрешить узел» (читает `+0x38`, при бит 30 рекурсивно собирает матрицу через `+0x13670`);
* `+0x193C0` — аллокатор **матриц** (не блоков).

**Арифметика падения.** Адрес обращения `0x1424 = 0x1400 + 0x24`. `0x1400 = 16 × 0x140`, то есть
`block->data == 0` (блок не выделен) при `индекс = 16`. Функция честно проверила `handle` на `-1`,
но **не проверяет, что блок вообще выделен**: берёт `block->data`, прибавляет смещение и читает.

### 2.1 Контекст: чей это метод и что за «переменная»

Vtable, в которой лежит упавшая функция, опознана через RTTI: `Complete Object Locator` по RVA `0x4C2E0`
(`pSelf` указывает сам на себя) → `TypeDescriptor` по RVA `0x55048` → **`.?AVi_gobjects@@`**.

| | |
|---|---|
| Объект | **`i_gobjects`** — граф игровых объектов движка (vtable RVA `0x49700`, **86 виртуальных методов**) |
| Упавший метод | **слот 32** = `+0x13120`: `void get_world_matrix(this, int handle, float out[16] /*r8*/, int tag /*r9d*/)` |
| Что делает | по «ручке» объекта берёт кэшированную мировую матрицу (попадание → `call [vtable+0xF8]`, копирование 64 байт); при устаревшей метке — пересчёт через `0x13AB0` (разрешение узла) и `+0x13670` (композиция) |
| «Переменная» | **ручка объекта**: `handle = (чанк << 10) | индекс_в_чанке`. В момент падения `handle = 16` → чанк **0**, индекс 16, и `таблица_чанков[0].data == 0` → чтение `0x1400 + 0x24 = 0x1424` |
| Поля объекта | `+0x168` — пул матриц (шаг `0x40` = 4×4 float); `+0x240` — таблица чанков (шаг `0x40`, первое поле — указатель на данные; на чанк `1024 × 0x140 = 0x50000` байт); элемент кэша `0x140` байт: `+0x24` — метка/«поколение», `+0x54` — слоты по `0x40` |
| Ручка `-1` | корневой узел: для неё берётся фиктивный чанк **перед** таблицей (`0x3FFFFFFFC0` = `-0x40` → `таблица[-1]`) |

**Соседний метод делает то же самое и тоже без проверки.** Слот 33 (`+0x13210`) содержит ровно то же
обращение — `cmp dword [rdi + 0x24], r13d` по адресу `+0x132C2`, перед которым такой же расчёт
`rdi = [this+0x240] + (handle>>10)*0x40` и `rdi += [rdi]`. То есть проверка отсутствует не в одном
забытом месте, а **во всём семействе методов**.

**Что уже закрыто — методы того же класса:**

* слот **25** = `+0x12920` — запись в кэш матриц (наш inline-патч границ на `+0x12925`),
* помощники `0x13AB0` (разрешение узла) и `+0x12FD0` (обход детей),
* слот **31** = `+0xFBA0` — «дай указатель на матрицу по ручке» (`[this+0x168] + resolve(handle)*0x40`);
  именно его вызывает упавший метод при попадании в кэш (`call [rax+0xF8]`).

> Коротко: **движок дёргает матрицу по «ручке», чей блок в пуле не выделен.**
> Чтение по нулевому указателю + смещение даёт адрес `0x1424` и ACCESS_VIOLATION.

Это в точности объясняет ваше наблюдение «падение в случайный момент, связи с действиями нет»:
момент зависит только от того, когда движок в очередной раз обратится к «протухшей ручке».

## 5. Побочные находки из этой же сессии

1. **Vitals: состояние ходит, но не применяется.**
   ```
   vitals: soldiers 917 dead 345, vehicles 32, applied 0 refused 50 ambiguous 0;
           channel sent 8441 acked 8441 rx 9631 retry 0 rejected 0 pending 0
   ```
   Канал **работает** (отправлено 8441, подтверждено 8441, принято 9631, повторов нет), раскладка
   `adv_physic` 3598/1 распознана, первичная проверка здоровья пройдена (40/40), хук статистики
   установлен. Но `applied 0` при `refused 50`: удалённые здоровье/смерть приходят, а запись в
   локальный объект бойца **отказывается** — ровно это вы видели как «солдаты не умирают».
   В сборке протокола 17 разбивка причин отказа не печаталась; **в текущей (протокол 18) она есть**:
   `vitals: refused in latest scan: invalid health N, death record/write N, health write N, …`.
   Нужно поставить 1.0.7 и посмотреть эту строку.

2. **У вас стояла промежуточная сборка (протокол 17), а не текущий установщик.**
   Модуль в процессе: SizeOfImage 450 560, timestamp `3512E4D8`, протокол 17.
   Наш `1.0.7 …NET+FPS_INSTALL.zip`: SizeOfImage 479 232, timestamp `55ACFD62`, **протокол 18**.
   Стоковый v20: 413 696 / `6ACFAA3D`. То есть дамп сделан **до** публикации текущего установщика.
   Хорошая новость: по коду защиты рендерера протокол 17 и 18 одинаковы — дыра на `+0x13120`
   есть и в текущем дереве (проверено по `render_guard.cpp`: закрыты только `0x12FD0`, `0x13AB0`,
   `0x12925`, `0x39A40`).

3. **Эталон игры в комплекте не совпадает с вашей копией.** Все 19 файлов из `x64.zip`
   не совпадают с `game_build_3598_1.sha256` из установщика — при том, что timestamp и размер
   образа совпадают. Скриптами этот файл **не используется** (проверено: `Check_Install.ps1`
   сверяет только `FILES_SHA256.txt`), так что это не поломка, а мусор, который введёт в заблуждение
   при ручной проверке. Стоит либо перегенерировать с вашей копии, либо убрать.

4. **Движок падает и без нашего мода.** Среди **35** уникальных сессий со стоковым модулем v12/v20 (13–27 октября)
   **7 оборваны без строки «unloaded»**. С нашим модулем: 6 тактических сессий — оборвана
   одна (эта); сессий карты операции 23 — оборвана одна (pid 12732, протокол 14). Повод не расслабляться, но и не валить всё на сеть.

## 6. Варианты исправления

Общее для всех вариантов: причина — внутри движка, «ручка» с невыделенным блоком появляется
не по нашей воле. Поэтому варианты — это либо перехват последствий, либо предпроверка.

### Вариант А. Ничего не менять
Принять, что движок падает сам по себе (это подтверждается и стоковыми сессиями).
**Риск:** падения продолжатся. **Цена:** 0.

### Вариант Б. Точечно: добавить сайт `+0x13184` в VEH
По образцу уже работающего обработчика: на чтение-AV с `Rip == +0x13184` проверить, что
`Rbp == *(таблица + (handle>>10)*0x40) + handle*0x140` и что `*(таблица + (handle>>10)*0x40) == 0`,
после чего восстановить выполнение. Вариант восстановления (выбираем по надёжности):

| | Как | Риск |
|---|---|---|
| **Б1** | записать в выход **единичную матрицу** (`out[0..0x3F] = I`) и уйти на эпилог `+0x131B1` | минимальный: объект на один кадр «без трансформа» |
| Б2 | подменить `rbp` на корневой узел-сентинел (`таблица[-1].data`) и пойти путём промаха `+0x131C1` | путь промаха читает `rbp + r9d*0x40 + 0x54` — чтение за границей сентинела |
| Б3 | лениво выделить чанк: `_aligned_malloc(0x50000, 0x40)` и записать указатель в таблицу | движок пойдёт своим путём; но потом чанк может быть освобождён движком — нужен тот же CRT |

**Плюс:** быстро, риск минимален (не подходит — не перехватываем).
**Минус:** закрывает 1 из 19 функций; следующее падение может быть в `0x13210` (слот 33) или `0x13550`.

### Вариант В. Системно: предпроверка на входе во все 19 акцессоров ★
Поставить детур на вход каждой функции семейства (14–15 байт пролога есть у всех),
в хуке — проверить `pool[handle >> 10].data != 0` (дешёвая проверка, без `VirtualQuery`),
и если блок пуст — сначала заставить движок его выделить (вызов аллокатора/«ensure»),
затем передать управление оригиналу. Всё остальное делает штатный код.
**Плюс:** закрывает всё семейство разом; логика та же, что у уже работающего `install_cache_bounds`.
**Минус/риск:** 19 детуров вместо одного; для каждой функции нужна своя байт-сигнатура входа
(механизм `hook_resolve_checked` уже умеет такое); если проверка по ошибке сработает на валидной
ручке — получим лишний вызов аллокатора, а не падение. Требует найти аллокатор блоков.

### Вариант Г. «Семейный» VEH
Расширить обработчик: ловить любое чтение-AV, где `Rip` внутри одной из 11 функций **и** адрес
обращения «низкий» (< 1 МБ) **и** адрес выводится из той же формулы. Восстановление — прежнее.
**Плюс:** один обработчик на всё семейство, не нужно 11 детуров.
**Минус:** для каждой функции нужен свой RVA «точки пересчёта» (аналог `0x13181`), то есть таблица
всё равно нужна; риск перехватить корректный отказ — выше, чем в варианте В.

### Вариант Д. Только диагностика
Добавить в guard счётчик и строку лога для падений внутри семейства, ничего не восстанавливая,
и собрать 3–5 новых дампов: понять, **повторяется ли именно `+0x13184` или «плавает» по функциям**.
От этого зависит выбор между Б и В/Г.
**Плюс:** честные данные вместо догадок; **Минус:** падения не прекратятся до следующего шага.

### Что я рекомендую
1. Поставить текущий установщик 1.0.7 (протокол 18) — иначе мы правим не то, что у вас запущено.
2. Сделать **Д + Б** (счётчик + точечный перехват `+0x13184`), а вариант В держать следующим шагом —
   как только поймём, «плавает» ли место падения.
3. Отдельно, независимо: разобраться с `vitals: applied 0 refused 50` по новой строке лога —
   это вторая по заметности проблема («солдаты не умирают») и она **не** связана с падением.

| 25.10 | `+0x129A2` | `0x12920..0x12A0C` | **`i_gobjects`, слот 25** | **write** `movaps [пул_матриц + (слот & 0xFFFFFF)*0x40]`, слот = `[элемент+0x34]` | закрыта (inline-патч `+0x12925` + VEH → `+0x129C6`) |
| 25.10 | `+0x39B52` | `0x39AB2..0x39DEE` (вызывается из `0x152DA`) | помощник, к графу объектов не относится | **read** вершин меша: индексы `[r8]`, `[r8+4]`, `[r8+8]` × шаг → `movups [индекс + буфер_вершин]` | закрыта (preflight + VEH → `+0x39DE5`) |
| **28.10** | **`+0x13184`** | `0x13120..0x1320A` | **`i_gobjects`, слот 32** | **read** `[элемент+0x24]` — метка/«поколение» кэша | **не закрыта** |

**Главный вывод.** Четыре падения из пяти — **один и тот же пул графа объектов `i_gobjects`**:
таблица чанков по `+0x240`, пул матриц по `+0x168`, элемент кэша `0x140` байт. Различаются только
поля элемента, к которым идёт обращение: `+0x38` (флаги/хэндл), `+0x34` (слот матрицы),
`+0x24` (метка). Пятое (треугольники) — другое: геометрия меша, а не граф объектов.

То есть мы трижды ловили одно и то же больное место по одному симптому за раз. Это прямо
подтверждает вариант **В** (закрыть семейство целиком), а не очередную точечную заплатку:
всего в модуле **19** функций с тем же разбором ручки, из которых **15 — виртуальные методы
`i_gobjects`**, и на сегодня закрыта ровно одна.
