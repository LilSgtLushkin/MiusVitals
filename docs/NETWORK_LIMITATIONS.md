# Известные ограничения сетевого кода и точные сайты в релизном модуле

Документ фиксирует **подтверждённые** дефекты релизного `basic_network.codelib` (Steam 6.00
build 3598/1, SHA-256 `485b6556…02a3`) и то, что из них реально можно исправить, не теряя
работоспособность мода. Он не описывает план правок: решения принимаются отдельно.

> **Статус на 2026-10-26: направление выбрано.** Исходника v20 нет и не будет, совместимость
> с v20 не требуется, поэтому фиксим то, что у нас есть: точечные патчи релизного модуля и
> новая логика в `mp_vitals.dll`. Код по-прежнему не изменялся, выпуска v1.0.2 нет; карта
> дефектов ниже остаётся актуальной. Процесс и границы — в
> [`SOURCE_REBUILD_REQUIREMENTS.md`](SOURCE_REBUILD_REQUIREMENTS.md), порядок переноса Vitals —
> в [`VITALS_CPP_PORT_PLAN.md`](VITALS_CPP_PORT_PLAN.md).

## 0. Граница документа

| Что | Как получено |
|---|---|
| Разметка модуля | PE-разбор: `.text` RVA `0x1000` (`0x42e68`), `.rdata` `0x44000`, `.data` `0x5a000`, `.pdata` `0x5f000`, `.reloc` `0x62000`, `.mpimp` `0x63000`; база образа `0x180000000`; timestamp `0x6ACFAA3D` |
| Границы функций | 895 записей `RUNTIME_FUNCTION` из `.pdata` (точные `Begin/End`, без эвристик) |
| Ссылки на данные | скан RIP-relative смещений по всему `.text`; адрес цели = `next_rva + disp32` |
| Константы | поиск битовых шаблонов `float`/`double`/`int` в `.text` + `.rdata` |
| Смысл кода | сверка с вендоренным публичным исходником `development/upstream/miusplayer-public-43b2736` |

Все RVA ниже — от базы образа. Правок в модуль не вносилось.

## 1. Что доказано о Steam-слое (граница «можно пересобрать / нельзя»)

В релизном модуле присутствуют строки и импорты Steam-слоя:

| Строка | RVA |
|---|---|
| `MP_STEAM_PEER` | `0x290768` |
| `SteamAPI_SteamFriends_v017` | `0x320000` |
| `SendP2PPacket` | `0x320602` |

В вендоренном публичном исходнике `basic_network/*.cpp|h` **нет ни одного** вхождения
`SteamAPI`, `SendP2PPacket` или `steam_api`: публичный снимок не содержит этого слоя.

Практический вывод: пересборка из публичного исходника **удаляет** Steam-друзей, приглашения и
P2P-канал, а `mp_vitals.dll` перестаёт находить свои сигнатуры (профиль RVA привязан именно к
релизному модулю). Поэтому все правки логики ниже помечены «source-only» и по умолчанию
не рассматриваются.

> Уточнение 2026-10-26: публичный C++ — это **v12**, а релизный модуль — **v20**; v20
> существует только бинарником в `GTMPRelease1.zip`. Пересборка из публичного дерева — не
> «v20 без Steam», а откат на v12: −293 функции, −~107 КБ кода. Подробности:
> [`UPSTREAM_V20_REPO_ANALYSIS.md`](UPSTREAM_V20_REPO_ANALYSIS.md).

## 2. Карта сайтов

### G1. Чужой HELLO принимается как пир и сбрасывает сессию

| Что | Где |
|---|---|
| Диспетчер пакетов (одна функция, сюда встаёт hook `mp_vitals`) | `0x16230`…`0x1755A`, hook-точка `0x1623A` |
| `g_tactical` | `0x5B618` |
| `g_have_peer = 1` | `0x169B4` |
| `g_connected = 1` | `0x169AD` |
| `g_peer = from` (16 байт `sockaddr_in`) | `0x169BB` |
| `g_last_rx = now` | `0x169C3` (и `0x169E5`) |
| Проверка «от пира» перед этими записями | **отсутствует** |
| Таймаут 8 с (`now - g_last_rx > 8000`) | `0x1AD53`…`0x1AD59` |

Следствие: HELLO с любого адреса проходит проверку версии и протокола, после чего ветка
«новый игрок» выполняет полный ресинк (`g_sent`, `g_held`, `statesync_reset`, `shots_reset`) —
это и есть «замирание» у обоих игроков.

**Исправимо из `mp_vitals.dll`**, без изменения модуля: в уже существующем `hook_packet`
отбрасывать `PKT_HELLO`, если `g_connected && (GetTickCount() - g_last_rx) < 3000` и адрес
отправителя не совпадает с `g_peer`. Риск: легитимный реконнект с другого порта ждёт до 3 с
(пир повторяет HELLO каждые 500 мс, восстановление автоматическое).

### G2. `MpVitalsInit` и порядок загрузки

| Что | Где |
|---|---|
| IAT-слот `mp_vitals.dll!MpVitalsInit` | RVA `0x631D8` (секция `.mpimp`) |
| Ссылок на этот слот из кода | **0** |

То есть экспорт используется только как якорь загрузки: модуль никогда не вызывает функцию.
Отсюда: «повторный `attach()` внутри `MpVitalsInit`» был бы **мёртвым кодом**. Реальная защита
от порядка загрузки — `DllMain` самой DLL, который выполняется, когда загрузчик разрешает
импорт уже отображённого `basic_network.codelib`, то есть когда модуль уже доступен.

Вывод: править нечего; если понадобится страховка, её надо делать таймером/потоком внутри DLL
(новый код и новый риск), а не в экспорте.

### G3. Экстраполяция не знает о паузе

| Что | Где |
|---|---|
| `session_sim_step` | `0x1C544`…`0x1D2D4` |
| `k_delay = 0.10` (double), `.rdata` | `0x4A288`; загрузка `0x1C929` в `xmm12`, применение `minsd` `0x1C97D` |
| `k_run_on = 0.25` (double), `.rdata` | `0x4A298`; загрузка `0x1C9B5` в `xmm10` |
| Применение `k_run_on` (кламп «догона») | `0x1CC78` (`minsd`), `0x1CC80` (`comisd` + `seta` → флаг `moving`), `0x1CFE1`/`0x1CFE8` |
| Флаг паузы в этом расчёте | не участвует (в исходнике `paused` хранится только как `g_host_paused` для ведомого таймера) |

`0x4A298` **разделена** с двумя несвязанными функциями (`0x20470` в `0x20190`…`0x207BF`,
`0x32114` в `0x32010`…`0x324FB`), поэтому править данные нельзя — только 4-байтное смещение в
`movsd xmm10,[rip+…]` по RVA `0x1C9B9`, направив его на слот с `0.0`.

Последствие такой правки: `run = 0` и `moving = false` всегда — экстраполяция выключается
**целиком** (в том числе когда она полезна). Правильное поведение («не экстраполировать только
на паузе») требует условной ветки, то есть исходника.

### G4. Порог «юнит сдвинулся» смотрит только первую строку поворота

| Что | Где |
|---|---|
| Функция отправки трансформов | `0x19B78`…`0x19CEE` |
| Позиция: `Σ|Δ|` против `0.002f` (`0x4A238`), `ja` → запись | `0x19CE0` |
| Поворот: `Σ|Δ|` против `0.0005f` (`0x4A234`), `ja` → запись | `0x19D3B` |
| Сравниваются только `[rsi+0x24]`, `[+0x28]`, `[+0x2C]` (строка 0 матрицы) | `0x19CE9`…`0x19D37` |
| Принудительная отправка: `2000 + 30·(i & 15)` мс | `0x19D44`…`0x19D5D` (`and eax,0xF`, `imul ecx,eax,0x1E`, `add ecx,0x7D0`) |

Дефект «крен/тангаж не считается движением» — **не константа**, а структура сравнения:
изменение только строк 1–2 даёт нулевую сумму при любом пороге. Константами не лечится;
`MP_IDLE_MS` (уже реализован в DLL) может лишь сократить худшее ожидание с 2–2,45 с до,
например, 1–1,45 с.

### G5. У потока трансформов нет бюджета байт и нет AOI

| Что | Где |
|---|---|
| Период снапшота 66 мс | `0x1ACC9` (`cmp eax,0x42`, функция `session_frame` `0x19F88`…`0x1B21F`) |
| Размер пакета | 24 + 14 × 80 = 1144 Б (`k_units_per_packet = 14`) |
| Учёт/ограничение скорости отправки | отсутствует (есть только счётчики статистики) |

300 юнитов: ⌈300/14⌉ = 22 пакета × 1144 Б × 15,15 Гц ≈ **381 КБ/с ≈ 3,0 Мбит/с** в каждую
сторону. Исправление (AOI, квантование, бюджет) — только исходник.

### G6. `MP_APPLY_DELAY` по стенным часам

| Что | Где |
|---|---|
| Чтение `MP_APPLY_DELAY` (строка `0x493A8`) | `0x1C5E5`…`0x1C5F2` (call `[0x1800441C0]` = `GetEnvironmentVariableA`) |
| `секунды × 1000` | `0x1C600` (`imul ecx,eax,0x3E8`) |
| Значение по умолчанию `0x2EE0` = 12000 мс | `0x1C608` (`mov ecx,0x2EE0`) |
| Запись в переменную | `0x1C60D` → `0x5A264` |

Патч не нужен: параметр уже настраивается переменной окружения `MP_APPLY_DELAY` (в секундах).
Уменьшать значение по умолчанию опасно: задержка введена именно потому, что загрузка state в
только что созданный бой ломала рендер крупных операционных боёв.

### G7. Дефекты, требующие пересборки исходника

`strcat_s` при построении `out`-пути; неограниченные карты `g_incoming`/`g_tracks`/`g_out` в
`statesync`/`shots`; таймстемпы снапшотов по QPС при переменной скорости симуляции;
`xlate::match()` с всегда истинным условием `(pass || true)`; отсутствие `static_assert` на
размеры пакетов; перебор указателей `i_render` в `find_device()`; полный сброс кэша текста в
`ui.cpp`; отсутствие резервной копии `tacgame_image.cfgpack` в `joiner.h`.

Все они находятся в коде, которого нет в публичном снимке в исполнимом виде (Steam-слой) либо
требуют пересборки, а значит — нового профиля RVA для `mp_vitals.dll` и нового полного
two-peer прогона. В текущей конфигурации не исправляются.

## 4. Как проверить, что ограничение всё ещё актуально

Сайты привязаны к конкретной сборке модуля. Перед любой правкой достаточно проверить, что
`SHA-256` файла равен `485b655662bd062e16278f9d699a3097b49a08de1948d2500dd589703a3102a3`
и что байты по адресам из таблиц совпадают с ожидаемыми: любое расхождение означает другую
сборку, и патч применять нельзя.
