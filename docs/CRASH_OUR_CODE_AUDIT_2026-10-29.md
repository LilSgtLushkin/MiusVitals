# Аудит нашего кода: что в нём может давать падения 28–29 октября

Дата: 2026-10-29. Ветка: `arena/d145e85b-miusvitals`.
Повод: «падения 100 % вызваны нашим модом» — проверить наши записи в память движка.
Материал: исходники `development/net-v21/src/`, разобранный дамп
(`docs/CRASH_DUMP_2026-10-28.md`), лог той же сессии.

---

## 1. Короткий вывод

Место падения находится в движке (`i_gobjects`, слот 32), но **причина в нашем коде**: мы пишем
трансформы удалённых юнитов напрямую по сырому указателю объекта, **не проверяя, что объект ещё жив**.
Если объект удалён, его память освобождена и переиспользована — мы портим то, что там теперь лежит.
Когда пострадавшая память оказывается книгой учёта пула рендерера, движок падает в случайный момент,
в другой подсистеме. Это классическое повреждение кучи, и оно полностью объясняет наблюдаемую картину:
«падение в случайный момент, связи с действиями нет».

Ключевое наблюдение: **все остальные наши подсистемы перед записью проверяют объект, а путь
трансформов — нет**, хотя он самый горячий: **22 650 записей в секунду** в упавшей сессии
(`sent 5468 and applied 113250 unit transforms` за 5 секунд).

---

## 2. Механизм повреждения

Объект юнита — это память движка. Мы пишем в неё 33 числа с плавающей точкой:

| Что | Смещение | Размер |
|---|---|---|
| позиция | `+0x1b0` | 12 байт |
| поворот 3×4 | `+0xf0` | 36 байт |
| обратный поворот 3×4 | `+0x130` | 36 байт |
| линейная скорость | `+0x1d0` | 12 байт |
| угловая скорость | `+0x1e0` | 12 байт |

(`common.h:15`.) Запись идёт через `write_remote_transform` (`transform_write.h:20-26`) — это голые
`memcpy` по переданным указателям, без какой-либо проверки цели.

Если объект к моменту записи удалён, эти 33 числа ложатся в память, которую аллокатор уже мог отдать
другому владельцу — в том числе под таблицу чанков графа объектов `i_gobjects` (`+0x240`) или под
элемент кэша (0x140 байт). Рендерер потом читает оттуда указатель на данные чанка, получает ноль и
падает ровно там, где мы видели: `+0x13184`, чтение `0x1424`.

---

## 3. Где именно у нас дыра

### 3.1 Главное: запись трансформов без проверки объекта

`session_sim_step()`, `session.cpp`:

```
1755    Object **all = all_objects(om, &count);            // снимок списка объектов
1756    if (!g_unit_list.matches(om, all, count)) rebuild_units(om, all, count);
1758    shots_sim_step(om);        // ← может убить юнит и удалить объект
1759    anim_sim_step(om, ...);    // ← тоже
1760    trench_sim_step(om);       // ← тоже
        ...
1835    char *u = (char *)it->second;                     // указатель из снимка
1859    if (!write_remote_transform(upos, urot, uinv, u + UNIT_LIN, u + UNIT_ANG, ...))
```

Три проблемы:

1. **Нет проверки жив ли объект.** Ни `readable()`, ни сравнения `o->objman == om`, ни проверки типа —
   ничего. Указатель берётся из `g_units`, построенного по снимку.
2. **Окно между снимком и записью.** Список берётся в строке 1755, а запись идёт в 1859 — **после**
   `shots_sim_step` / `anim_sim_step` / `trench_sim_step`, которые сами могут уничтожить объект.
3. **Снимок не ловит переиспользование адреса.** В нашем же коде это признано дословно
   (`transform_gc.h:10-11`): снимок обнаруживает замену и переупорядочение указателей, но
   «not destruction and reuse at the same address between two observations».

### 3.2 Контраст: так делают все остальные наши подсистемы

| Подсистема | Проверка перед записью |
|---|---|
| `anim_sync.cpp:55` | `readable(o, 0x1efc)` + `o->objman == manager` + `memcmp(o->iface, "i_human", 8)` + `session_unit(*key) == o` |
| `anim_sync.cpp:282-283` | `writable(inst, …)` для каждого адреса записи |
| `hit_sync.cpp:36` | `readable(o, sizeof(Object))` + `o->objman == g_om` + `readable(o->iface, 8)`; плюс свой `writable()` (`:24`) |
| `vitals.cpp:128-129` | `readable(o, sizeof *o)` + `o->objman == om` + `memchr(o->full, 0, …)` |
| **`session.cpp:1835-1866` (трансформы)** | **ничего** |

`readable()` — это `VirtualQuery` (`basic_network.cpp:67`), `writable()` — то же плюс проверка
защиты страницы (`anim_sync.cpp:44-52`). Инструмент в коде уже есть и уже применяется везде, кроме
самого горячего пути.

### 3.3 «Конец боя / ESC / перезапуск поиска»

`g_tactical` — это **признак программы**, а не боя: `session.cpp:1483`
(`g_tactical = !strcmp(g_program, "tacgame")`). Он остаётся `true` весь процесс, поэтому
`session_sim_step` продолжает писать трансформы и тогда, когда бой уже завершается и движок
разбирает объекты. `session_stop()` чистит кэши только внутри `if (g_tactical)`
(`session.cpp:1623-1631`), а других мест, где кэши сбрасывались бы при смене фазы, нет
(это же находка **Н-2** вчерашнего ревью: `session.cpp:1716-1726`).

### 3.4 Запись блоба состояния (в операционном бою отключена)

`statesync.cpp:318-330`: индекс `g_state_index` перестраивается только когда изменилось
**количество** объектов (`if (count != g_state_seen_count)`). Удаление плюс вставка оставляют
число прежним, а часть указателей — протухшей; затем `state_load_keep_motion()` (`state.cpp:241`)
записывает в объект **целое сохранённое состояние**. В дампе от 28.10 это отключено
(операционный бой → `default_full_state() == false`), но в тактических боях включено — там объём
разовой записи на порядок больше, чем у трансформов.

### 3.5 Мелкое

* `vitals.cpp:166-181` — `set_health()` / `mark_dead()` пишут без `writable()`, но объект
  проверен `readable()` выше по тому же проходу (`vitals.cpp:325`), так что риск ниже.
* Наши хуки рендерера проверены и в этом смысле чисты: восстановления VEH (`+0x13BC9`, `+0x13038`,
  `+0x129C6`) уходят **до** выставления служебного бита 0x1e, то есть не оставляют узла
  «в обработке». `render_cache_preflight` (`render_guard.cpp:207-230`) сам пишет в слот движка
  (`+0x34`), но делает это только после проверки читаемости каждого шага.

## 4. Почему это выглядит как «падение движка»

Повреждение памяти проявляется не там, где его нанесли, и не тогда. Мы пишем в освобождённый блок в
момент **T**, а движок читает пострадавшую память в момент **T + Δ**, в другой подсистеме, на другом
кадре. Отсюда и все признаки:

* падение в рендерере, хотя сеть ни при чём;
* случайный момент, без связи с действиями игрока;
* адрес обращения мусорный (`0x1424`), а не «наш»;
* наш guard не может ничего предотвратить: он ловит уже **следствие** — обращение к невыделенному
  чанку, — и не в силах вернуть испорченную книгу учёта.

## 5. Что предлагаю исправить (и в каком порядке)

| # | Что | Где | Эффект |
|---|---|---|---|
| 1 | Проверять объект перед записью трансформа: `readable(o, …)`, `o->objman == om`, тип из `iface`, `writable()` на каждый целевой адрес — по образцу `anim_sync.cpp:55` / `hit_sync.cpp:36` | `session.cpp:1835-1866` | убирает сам механизм повреждения |
| 2 | Убрать окно: перепроверять список объектов (или.refresh `g_units`) **после** `shots/anim/trench` и перед записью | `session.cpp:1755-1859` | закрывает «уничтожение внутри шага» |
| 3 | Инвалидировать кэши при смене фазы/конце боя, а не только в `session_stop()` | `session.cpp:1716-1726` (Н-2) | сценарии «конец боя / ESC / поиск» |
| 4 | Перестраивать `g_state_index` не по количеству, а по содержимому списка | `statesync.cpp:318-330` (Н-1) | тактические бои |

### 5.1 Как именно проверять: цена решает

Проверка уже написана, собрана и прогнана по шагам: `src/transform_object_check.h` +
`tests/transform_object_check_test.cpp` (последний собирается в Linux без игры, зондирование
читает настоящую `/proc/self/maps`). Результат: **37 проверок, 0 провалов**, трейс каждого шага
для одиннадцати фикстур (исправный юнит, нулевой указатель, освобождённая память, страница только
для чтения, чужой менеджер, не юнит, битый `iface`, имя без нуля, подмена объекта в индексе,
выход за границу региона, несовпадение вида).

Но **проверять каждую запись через `VirtualQuery` нельзя** — это слишком дорого:

| | |
|---|---|
| записей в секунду | 22 650 (из лога упавшей сессии) |
| зондирований на запись | 8 (объект, `iface`, имя и пять полей движения) |
| итого зондирований в секунду | ≈ 181 000 |
| `VirtualQuery` (оценка, Windows) | ≈ 1–3 мкс (не измерено здесь — MSVC и Windows недоступны) |
| стоимость | **≈ 0,2–0,5 с процессорного времени каждую секунду**, то есть 18–54 % ядра |

Поэтому в бою проверка трёхслойная, по образцу того, что уже делает наш же код:

1. **Дешёвые проверки без syscall** (~50 нс на юнит): указатель не нулевой; `o->objman == om`;
   вид по `iface`; имя экземпляра завершено нулём; сверка с живым индексом
   (`session_unit(key) == o`). Это ловит главный случай — «объект удалён, по тому же адресу уже
   другой».
2. **Страховка `__try / __except` вокруг самой записи** — ноль стоимости, когда всё в порядке,
   и перехват `EXCEPTION_ACCESS_VIOLATION`, если память всё-таки освобождена. Ровно так уже
   сделано в `anim_sync.cpp:140`, `hit_sync.cpp:208`, `render_guard.cpp:327`.
3. **`VirtualQuery`-проверка только в режиме трассировки** (`MP_TRACE_WRITES=1`): построчный
   разбор каждого юнита, причина отказа и счётчики — для отладки на живой игре, а не на каждый кадр.

### 5.2 Компиляция и отладка: что доступно, а что нет

| | |
|---|---|
| Портируемую проверку (без `windows.h`) | **собрана и прогнана здесь**, g++ на Linux |
| Сам модуль `basic_network.codelib` | здесь собрать нельзя: это Windows-DLL, собирается MSVC (`build.bat`); в песочнице нет ни Windows, ни MSVC |
| Артефакты CI | скачать себе я не могу: файлы Actions лежат на `blob.core.windows.net`, он закрыт сетевой политикой песочницы. **Вы** их скачиваете со страницы Actions без проблем |

Отсюда рабочий порядок: задание в CI собирает инструментированный модуль (MSVC, `/Od /Zi`,
плюс env-трассировка) и выкладывает его артефактом PR — вы скачиваете, кладёте в игру и
получаете построчный лог по каждому юниту и каждой записи.

Пункты 1–2 — это около 30 строк и один самотест: проверку можно вынести в портируемый хелпер рядом
с `transform_write.h` и покрыть тестами без Windows-заголовков (как делает `render_cache_bounds.h`).

**Что это меняет в плане работ.** Варианты Б/В по рендереру (`docs/CRASH_DUMP_2026-10-28.md`,
раздел 6) лечат симптом: они спасут от падения в `+0x13184`, но не от того, что мы продолжаем
портить память — следующее падение будет в другом месте. Причинное исправление — пункты 1–2 этого
документа. Guard имеет смысл оставить как страховку, но не вместо них.
