### 2.6 Транспорт

* Один шлюз отправки `send_to()`; адрес с семейством `0x5354` уходит в Steam P2P, иначе — в UDP.
* Steam: `kSendType = SEND_UNRELIABLE` (`steam.cpp:106`), канал один на всё (сессия и Joiner делят очередь, арбитраж через `steam_lobby_receiving()`).
* Надёжность (**выстрелы, окопы, таблицы номеров, Vitals, фрагменты состояния**) реализована сверху: `retry_gate.h` + `reliable_inbox.h` + ACK.
* **Трансформы (`PKT_STATE`) идут без подтверждения и не повторяются**: отправитель шлёт только то, что изменилось с прошлого раза (`transform_send.h`).

## 3. Найденные проблемы

Приоритет: **P1** — вероятная причина вылетов/сильных глитчей; **P2** — важная, но косвенная; **P3** — качество и запас.

### Н-1 (P1) Устаревший индекс объектов в репликации состояния: запись блоба в мёртвый или чужой объект

**Где:** `development/net-v21/src/statesync.cpp:228-229`, `318-330`.

```cpp
static std::unordered_map<u64, Object *> g_state_index;
static u32 g_state_seen_count = 0xffffffffu;
…
if (count != g_state_seen_count) {            // ← индекс сбрасывается ТОЛЬКО по изменению ДЛИНЫ
    g_state_index.clear();
    for (…) g_state_index[statesync_key(all[i])] = all[i];
    g_state_seen_count = count;
}
…
Object *o = it->second;                       // ← может быть уже не тем объектом
state_load_keep_motion(o, in.base.data(), in.base.size(), …);
```

**Механика.** Кэш «ключ → указатель» живёт, пока не изменилось **число** объектов. Если юниты удалены и созданы заново (конец боя, второй раунд, переподключение, смена отделения/подкрепление), длина списка легко остаётся прежней, а объекты по адресам — уже другие или освобождены. `state_load*` пишет в объект сотни байт сохранённого состояния.

**Симптом.** Повреждение кучи движка → падение **не там, где причина**; характерно падение в `basic_render.codelib` (кэш матриц/материалов) через несколько кадров. В точности совпадает с профилем «вылет в конце боя / при перезапуске поиска».

**Почему похоже на правду.** Полная репликация состояния **включена по умолчанию** во всех режимах, кроме операционных боёв (`tactical_mode.h: default_full_state()` → `host_mode != HOST_MODE_OPERATION`). Ваши удачные прогоны — скримиш 8×8 (репликация **вкл**), и именно там проблемы; туман войны/операция — отдельная история.

**Риск исправления:** низкий. **Цена:** правка в 2 местах.

### Н-2 (P1) Тот же класс для трансформов, но защита сильнее и всё равно неполная

**Где:** `session.cpp:1716-1726` (`rebuild_units`), `transform_gc.h:14-22` (`ObjectListSnapshot::matches`).

Здесь сравнивается уже **весь массив указателей**, а не только длина — это лучше, чем в Н-1. Но в самом файле честно написано:

> «This detects pointer replacement/reordering, **not destruction and reuse at the same address** between two observations; the engine does not expose a generation here.»

Дальше каждый шаг симуляции, для каждого ведомого юнита, **без проверок** выполняется запись 5 массивов в кэшированный указатель (`session.cpp:1860` → `transform_write.h`), плюс `owns_object()`/`unit_key()` разыменовывают `o->iface` и `o->full`.

**Симптом:** запись в освобождённую память; либо (мягче) «не тот» объект начинает ездить по чужим координатам.

**Дополнительно:** `g_held`/`g_units` не чистятся при уходе из фазы 2 (конец боя) — только в `session_stop()`.

### Н-3 (P1) Нет барьера исключений на путях приёма пакета и кадра

**Где:** `session.cpp:2756` `on_packet()`, `3252` `session_frame()`, `1733` `session_sim_step()`. Единственный `try/catch` во всём модуле — вокруг `engine_find` в `basic_network.cpp:135`.

Сборка идёт с `/EHa`, STL используется повсеместно (`std::vector`, `std::unordered_map`, `std::string` — выделения могут бросить `bad_alloc`). Показательный пример: `session.cpp:3044` выделяет память **до какой-либо проверки**, по присланному пиром размеру:

```cpp
g_map_in.assign(w->map_size, 0);                                   // map_size — unsigned из пакета
g_map_have.assign((w->map_size + k_chunk - 1) / k_chunk, 0);       // + переполнение по модулю 2^32
```

(Проверка размера есть, но уже во фрагментах — `image_chunks::valid()` отвергает `total > 64 МБ`, — а здесь её нет.)

**Симптом:** исключение уходит через кадры движка → падение без внятной записи в логе.

**Риск исправления:** минимальный. **Цена:** обёртка `try/catch(...)` + лог + проверка `map_size` до выделения.

### Н-4 (P2) Буфер интерполяции меньше интервала отправки — «мерцание гусениц» и рывки

**Где:** отправка — `session.cpp:3366` (`now - g_last_snapshot >= 66`, то есть ~15 Гц); приём — `session.cpp:1792` (`k_delay = 0.10`, `k_run_on = 0.25`).

* Буфер 100 мс при интервале 66 мс — это всего **~1.5 пакета** запаса. Любой джиттер/потеря больше 34 мс — и буфер пуст.
* Потерянный `PKT_STATE` **не повторяется** (не подтверждается и не перепосылается).
* При пустом буфере включается «доезд» по последней скорости на 250 мс, потом юнит **встаёт** (`moving = false`, скорости обнуляются), а следующий пакет **дёргает** его на новое место. Счётчик таких рывков и есть `net: … largest correction unit=…` и `jumps` в 5-секундном отчёте.
* В ветке «доезд» extrapolируется **только позиция**, поворот берётся как есть (`memcpy(rot, B.rot, …)`) → поворачивающая техника «замирает» и потом доворачивает рывком. Именно это визуально больше всего заметно на гусеницах: их прокрутка считается движком из пройденного расстояния.
* Окно интерполяции жёстко ограничено 0.6 с (`h.b.at - h.a.at < 0.6`) — при более редких пакетах blend не работает вообще.

**Что мерять:** в логе строки `net: 5 s: sent … applied … mean correction … largest … jumps …` и `net: largest correction unit=…`. Если `largest correction` стабильно больше ~1 м, а `jumps` растёт — это Н-4.

### Н-5 (P2) Отправка трансформов и часов завязана на эпохи Vitals

**Где:** `session.cpp:1655`:

```cpp
sh->owner = vitals_epoch(); sh->target = vitals_peer_epoch();
if (!sh->owner || !sh->target) return;   // не уходят НИ трансформы, НИ часы
```

Эпохи — механизм защиты от пакетов «из прошлой битвы». Но здесь он стал **единой точкой отказа для двух независимых подсистем**: если рукопожатие Vitals не состоялось (или эпоха признана retired — `vitals_peer()` может отказать), позиции и часы **не идут вовсе**. Учитывая, что в 1.0.7 Vitals «не работал», первым делом надо посмотреть в логе строки `vitals:` — были ли эпохи ненулевые.

### Н-6 (P2) Хуки скорости/паузы ставятся один раз на процесс

**Где:** `session.cpp:2035` `replace_timer_setters()` — `static bool done` и `static void *copy[65]`.

Если вторая битва запускается в том же процессе, новый объект таймера остаётся без подмены vtable, и «часы — хозяйские» перестают действовать. Судя по коду, `tacgame` и `opgame` — разные программы и состояние между ними передаётся через переменные окружения (`MP_MAP_EPOCH` и т.п.), т.е. обычно это новый процесс. **Требует проверки вживую:** если битву можно перезапустить без выхода в меню — это баг.

### Н-7 (P2) Нет проверок доступности памяти в горячем пути

`unit_key()` (`session.cpp:487`), `owns_object()` (`:528`) и `write_remote_transform()` (`transform_write.h`) работают с объектом без `readable()`. Для «свежего» указателя это нормально (список только что переиндексирован), но в сочетании с Н-1/Н-2 это ровно тот путь, которым портится память. Проверка «объект всё ещё в списке и его ключ совпадает» стоит одну сверку на юнит за шаг — на сотнях юнитов незаметно.

### Н-8 (P3) Порог отправки «всё, что шевельнулось» и ограниченный приём

**Где:** `transform_send.h:14-24` — позиция > 0.002 (L1) или любая строка поворота > 0.0005 → отправка. Приём: ≤ 64 датаграммы Steam за кадр (`session.cpp:3285`).

Для 8×8 это до ~15 Гц × ⌈N/14⌉ датаграмм в секунду (при 80 своих юнитах ≈ 90 пакетов/с, ~100 КБ/с). Приём ограничен 64 за **кадр** — на низком FPS очередь растёт, задержка растёт, и это напрямую усиливает Н-4. Померить: `rx … / tx … KB/s` в 5-секундном отчёте.

---

### Н-9 (P3) Мелкое, но важное для повторяемости

* `session_stop()` (`session.cpp:1606`) не сбрасывает `g_phase`, `g_my_ready`, `g_peer_ready`, `g_pause`, `g_host_speed/paused`, `g_have_host_clock`, статистику. Если codelib между битвами не выгружается — вторая битва стартует с мусором (проверить вместе с Н-6).
* `render_guard_install()` вызывается только при `g_tactical` (`session.cpp:1738`, `:3272`) — падения рендерера на операционной карте и в меню не перехватываются.
* VEH-обработчик покрывает **ровно** 4 известных адреса (+ 12 IP в треугольниках). Новое место падения он не поймает — это нормально, но объясняет, почему «защита есть, а игра всё равно падает».
* `prune_replaced()` чистит кэши трансформов только при перестроении списка (см. Н-2).

### Н-10 (несовместимость, информационно) Старая `mp_vitals.dll` в комплекте

Архив кладёт `mp_vitals.dll` (40 960 Б, экспорт `MpVitalsInit`) в корень игры. Проверено: **наш модуль её не импортирует** → она инертна, двойных хуков нет. Более того, сам `render_guard` предупреждает в логе, если кто-то другой её загрузит. **Но**: старый sidecar исторически подключался правкой таблицы импорта v20-модуля, так что на машине, где раньше стоял v20-комплект, DLL могла грузиться раньше; сейчас она мертва. Вопрос к вам: оставить её в комплекте (безобидно, но сбивает с толку и её ищет `Collect_Logs.ps1`) или убрать.

## 4. Старые дампы: что они доказывают и что с ними сделано

Все четыре класса — в `basic_render.codelib` сборки 3598/1, timestamp `0x66f2d710`, то есть **в том же самом образе рендерера, под который собрана текущая сборка**. Анализы: `docs/CRASH_ANALYSIS_2026-10-24.md`, `docs/CRASH_ANALYSIS_2026-10-25.md`, `docs/RENDER_CACHE_ROOT_CAUSE_2026-10-25.md`, `docs/TRIANGLE_GEOMETRY_ROOT_CAUSE_2026-10-25.md`.

| # | Место | Тип | Дамп (SHA-256) | Что в текущей сборке |
|---|---|---|---|---|
| 1 | `+0x13adb` `mov ecx,[rsi+0x38]`, рекурсивный чтёлка материала (`+0x13ab0`, эпилог `+0x13bc9`) | read AV | `c5befc49…` (тред 31832), `2d0d4da6…` (тред 7048) — **самые старые, до первых фиксов** | VEH: пропуск ветки, `Rip → +0x13bc9`, родительский материал в `EDI` |
| 2 | `+0x12ffd` `8b 4f 38`, обход детей (`+0x12fd0`, эпилог `+0x13038`), `R8 = 0x3f800000` | read AV | `gt3_crashreport.zip` | VEH: `Rip → +0x13038` |
| 3 | `+0x129a2` `movaps [rax+rcx],xmm0` — **устаревший слот кэша матриц** | write AV | `0a75452e…` | быстрый inline-патч границ `+0x1298f` (по умолчанию) + VEH → аллокатор `+0x129c6`; строгий preflight — по запросу |
| 4 | `+0x39b52` `movups xmm9,[rax+rsi]`, запрос геометрии (`+0x39a40`, no-hit `+0x39de5`) | read AV | `01051fc8…` | preflight + VEH по 12 IP |

**Ключевое наблюдение по «дампам до первых фиксов».** В старом sidecar `mp_vitals.dll` уже были все три первые защиты — его строки это подтверждают: `vitals: skipped an invalid recursive basic_render node`, `vitals: rebuilt %u stale basic_render transform cache entr%s through the engine allocator`, `vitals: skipped %u malformed basic_render geometry read%s`. При этом как минимум в дампе `2d0d4da6…` **`mp_vitals.dll` вообще не был загружен**. То есть старые дампы:
1. доказывают **собственный дефект рендерера движка** (устаревшие/битые данные в кэше матриц и в геометрии) — он никуда не делся, образ тот же;
2. **не** доказывают, что причина — наша сеть: protection тогда просто не была установлена;
3. честно очерчивают границу: VEH ловит только эти адреса.

Управление с текущей сборкой:
* `MP_RENDER_GUARD=0` — выключить VEH-восстановление (для диагностики «ловит или нет»);
* `MP_RENDER_CACHE_GUARD=strict` — дорогой preflight кэша (по умолчанию **не** включается, даже если быстрый патч не встал);
* в логе раз в 5 с: `render guard: total child branches recovered N, cache strict/fault repairs N, bounds repairs N, geometry queries skipped N, preflight races N`.

**Вывод:** старые дампы закрыты *реактивно*. Текущие сценарии (отключение во время подключения, конец боя, перезапуск поиска, ESC) — скорее всего **другой класс**, и по старым дампам его не доказать. Нужны свежие `out\minidump.dmp` из 1.0.7.

## 5. Варианты исправления вылета (с учётом того, что код теперь свой)

Ниже — варианты от «дешёвого и безопасного» к «сильному, но меняющему поведение». Я не начинал их реализовывать: сначала нужен ваш выбор, потому что часть вариантов меняет игровые возможности.

### Вариант А. Оставить реактивную защиту как есть
**Что:** текущий VEH + быстрый патч кэша. **Плюс:** ноль риска, ноль работы. **Минус:** перехватывает только 4 известных адреса; если падение новое (а Н-1/Н-2 дают именно «новые»), игра падает. **Оценка:** как самостоятельное решение — недостаточно.

### Вариант Б. Убрать источник: строгая валидация перед каждой записью в объект ★ рекомендую первым
**Что:**
1. `statesync.cpp`: перестать инвалидировать индекс по одной длине — использовать тот же `ObjectListSnapshot` (сравнение всего массива указателей + смена менеджера), и перед загрузкой сверять `readable(o, …)`, `iface` и ключ.
2. `session.cpp`: перед `write_remote_transform()` проверять, что объект всё ещё числится под тем же ключом; чистить `g_held`/`g_units` при уходе из фазы 2 и при `session_stop()`.
3. Инвалидировать оба кэша на смене объект-менеджера и не реже раза в N секунд (страховка от «тот же адрес»).
**Плюс:** убирает весь класс «причина в одном месте, падение в другом». **Минус/риск:** одна-две сверки на юнит за шаг — по моей оценке менее 0.05 мс на кадр при сотне юнитов; логику не меняет. **Оценка:** низкий риск, высокий шанс закрыть «конец боя/перезапуск».

### Вариант В. Отключить полную репликацию состояния (по умолчанию или через `MP_SYNC_STATE=0`)
**Что:** не заливать чужие блобы состояния в объекты; позиции/выстрелы/попадания/ Vitals/окопы остаются. В операционных боях так **уже** работает по умолчанию (`tactical_mode.h`).
**Плюс:** самый сильный подозреваемый (Н-1) выключается целиком, заодно уходит известный дефект «некоторые модели техники не переживают загрузку чужого состояния» (сейчас он обходится списком `MP_STATE_SKIP`: `opel,zis5,zis_5,gaz_aa,gaz_mm,truck`).
**Минус:** теряется синхронизация «внутренностей» — боекомплект, повреждения узлов, состояние экипажа, возможно двери/люки. **Оценка:** сначала как **диагностический выключатель** (один прогон), потом решаем.

### Вариант Г. Точечно расширить список «только позиция» (`MP_STATE_SKIP`)
**Что:** механизм уже есть (`session.cpp:496 find_position_only_units`). Добавить модели, на которых падает.
**Плюс:** минимально инвазивно. **Минус:** лечит симптом на конкретных моделях, требует знать список. **Оценка:** как дополнение к В, а не вместо.

### Вариант Д. Расширить защиту рендерера
**Что:** (1) прогнать с `MP_RENDER_CACHE_GUARD=strict`; (2) после получения **свежих** дампов добавить новые адреса в VEH; (3) включить `render_guard_install()` вне тактики.
**Плюс:** закрывает то, что уже известно. **Минус:** strict стоит FPS (per-call `VirtualQuery`), новые адреса без дампов угадывать нельзя. **Оценка:** только после дампов; до них — пустая трата времени.

### Вариант Е. Барьер исключений + валидация размера карты ★ рекомендую вместе с Б
**Что:** обернуть `on_packet`, `session_frame`, `session_sim_step` в `try/catch(...)` с записью в лог; проверять `map_size` **до** `g_map_in.assign()`.
**Плюс:** превращает «падение без следа» в строку лога; убирает вектор с пакетом от пира. **Минус:** может скрыть проблему, если не смотреть логи — поэтому обязателен лог. **Оценка:** минутное дело, риск нулевой.

### Вариант Ж. Сетевая часть jitter (Н-4, Н-5)
**Что:** поднять буфер интерполяции до 150–200 мс (или «2× интервал + джиттер»), экстраполировать поворот по угловой скорости, развязать отправку часов/трансформов от эпох Vitals (Н-5), поднять лимит приёма Steam.
**Плюс:** langsung влияет на «мерцание гусениц». **Минус:** бутер интерполяции добавляет задержку отклика (0.1 → 0.2 с) — заметно ли, надо probar вживую. **Оценка:** средний риск, нужен A/B прогон.

## 6. План диагностики (то, что можно сделать без правок кода)

Все переменные задаются до запуска игры, эффект виден в `out\basic_network_tacgame_<pid>.log`.

| Шаг | Переменная | Если падения/глитчи исчезли |
|---|---|---|
| 1 | `MP_SYNC_STATE=0` | виновна запись чужих состояний → **Н-1**, выбираем вариант В/Г |
| 2 | `MP_APPLY_DELAY=3600` | виновна запись трансформов → **Н-2**, выбираем вариант Б |
| 3 | `MP_RENDER_GUARD=0` | падения участились → guard реально ловил; смотрим счётчики `render guard: total … repairs` |
| 4 | `MP_RENDER_CACHE_GUARD=strict` | помогло → класс №3 (кэш матриц), быстрого патча мало → вариант Д |
| 5 | ничего, просто играть | смотреть каждые 5 с: `net: 5 s: … mean correction … largest … jumps … rx/tx KB/s` и `net: largest correction unit=…` |

**Что нужно от вас для точного диагноза:**
1. Свежий `out\minidump.dmp` **сразу после падения** из 1.0.7 (и, по возможности, не один). `Collect_Logs.ps1` дампы принципиально не собирает — их надо копировать руками. Сводку по дампу делает `development/upstream/miusplayer-public-43b2736/tools/crash_info.py`.
2. Логи `out\basic_network_*.log` обоих игроков за тот же прогон.
3. Ответ по сценариям: падение происходит **в момент** отключения/конца боя или через несколько секунд после? Это разделяет «наш код пишет в мёртвое» (Б/В) от «движок сам» (Д).

## 7. Границы этого ревью (честно)

* Не собирался и не запускался Windows-модуль: MSVC и игра в песочнице недоступны. Всё, что связано с реальным таймингом, потоками движка и живыми объектами, проверено только кодом, тестами и логами.

* Утверждение «поставляемый бинарник = текущие исходники» опирается на совпадение 662/675 строк и на CI-происхождение (source commit `482c5edb`); побайтовую репродуцируемость сборки здесь проверить нельзя.
