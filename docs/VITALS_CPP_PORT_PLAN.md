# План переноса логики `mp_vitals` в C++ (поэтапно, с откатами)

Одобрено 2026-10-26. Правило пользователя: **медленно, спланированно, с постоянными
тестами и откатами**. Приоритет — 100% работоспособность мода: любой этап, ухудшивший
поведение, откатывается целиком, а не «дожимается на ходу».

## 0. Что именно мы переносим и чего перенести нельзя

`mp_vitals.dll` (сейчас 1 372 строки, собрана Zig, импортирует только `KERNEL32`,
экспорт `MpVitalsInit`) — это **наш** код: он целиком в репозитории, у него есть исходник.
Он не «часть v20», а слой поверх него: два хука (`session_frame`, `on_packet`), VEH-guard
для `basic_render`, хук статистики и патч idle-периода.

Перенос в C++ **не означает** встраивание в `basic_network.codelib`: исходника v20 нет,
вкомпилировать в него нечего. Поэтому цель переноса — не «убрать DLL», а:

1. **структура** — вместо одного файла на 1 372 строки модули с явными границами;
2. **тестируемость** — вся работа с движком за одним интерфейсом, значит логику можно
   прогонять на подставном хосте без игры;
3. **снижение хрупкости** — профиль RVA и сигнатуры становятся данными с самопроверкой и
   понятным отказом, а не россыпью констант;
4. **предсказуемые откаты** — каждая подсистема включается/выключается отдельно.

Чего перенос **не** делает: не улучшает v20-код, не меняет сетевой протокол, не убирает
`.mpimp` (импорт `mp_vitals.dll!MpVitalsInit` остаётся способом загрузки).

## 1. Незыблемые инварианты (проверяются на каждом этапе)

| # | Инвариант | Как проверяется |
|---|---|---|
| I1 | DLL импортирует **только** `KERNEL32`, экспорт — `MpVitalsInit` | `scripts/check_artifacts.py`, `objdump -p` |
| I2 | При несовпадении сборки игры **ни один хук не ставится** | лог `vitals: ... not installed`, прогон на чужом билде |
| I3 | Нативные типы пакетов проходят в MiusPlayer **без изменений** | трасса `compare_traces.py`: типы 10/11 и все прочие байт-в-байт |
| I4 | Наши типы — только резервные `0x34`/`0x35` | grep по коду + трасса |
| I5 | Никаких исключений наружу: VEH обрабатывает только подтверждённые чтения | ревью сигнатур + дампы |
| I6 | Vitals никогда не «лечит вверх»: состояние только ухудшается | юнит-тесты монотонности |

## 2. Точки отката

* `v1.0.1` — последний опубликованный комплект (baseline сегодняшнего прогона).
* Каждый этап — **отдельный коммит** и тег `port/E<n>` в ветке; откат = `git revert`
  одного коммита или возврат тега.
* На всё время порта в DLL живут **две реализации**: старая (`legacy`) и новая (`new`),
  переключаемые `MP_VITALS_IMPL=legacy|new` (по умолчанию — `legacy` до приёмки этапа).
  Это позволяет откатиться без перевыпуска архива — достаточно переменной среды.
* Этап считается принятым только после двух-ПК прогона по
  [`TWO_PC_TEST_PLAN_2026-10-26.md`](TWO_PC_TEST_PLAN_2026-10-26.md) (сокращённый набор
  S1/S2/S4) и совпадения логов `vitals:` с legacy-прогоном.

## 3. Целевая структура

| Модуль | Ответственность | Строк сейчас |
|---|---|---|
| `host/` | интерфейс к codelib: хуки, глобалы, вызовы движка, проверка страниц памяти | ~250 |
| `profile/` | PE-профиль: timestamp, RVA, сигнатуры, самопроверка, причина отказа | ~200 |
| `engine/` | чтение/запись объектов игры: солдат, отряд, техника, статистика | ~300 |
| `net/` | типы `0x34`/`0x35`: epoch/seq, mailbox, ACK, retry, дедупликация | ~200 |
| `vitals/` | монотонное состояние: здоровье, смерть, флаги техники | ~200 |
| `render/` | guard'ы `basic_render`: кэш, геометрия, invalid child | ~350 |
| `app/` | `MpVitalsInit`, разбор env, порядок инициализации, лог | ~120 |
| `tests/` | юнит-тесты на подставном хосте | — |

Требование сборки: C++ без CRT (`/nodefaultlib`, без исключений/RTTI, без `new`), чтобы
сохранить I1. Это не ограничение языка, а ограничение линковки: в DLL не должно появиться
ни одного импорта, кроме `KERNEL32`.

## 4. Этапы

### E0. Baseline и фиксация профиля — *без изменений кода*

* Прогон v1.0.1 на двух ПК, сохранение логов и хешей.
* Профиль (RVA + сигнатуры) выгружается в человекочитаемый вид и сверяется с тем, что
  реально в памяти, на обоих ПК.
* **Приёмка:** логи обоих ПК, совпадающие хеши, `build_report.txt`.
* **Откат:** не требуется.

### E1. Разделение на модули без изменения поведения

* `mp_vitals.c` → `src/vitals/*.cpp` (или `.c`, собираемые как C++), один и тот же
  алгоритм, перенос строка-в-строку, без «улучшений».
* Обе реализации (`legacy` из git-тега, `new`) собираются в одну DLL и включаются
  `MP_VITALS_IMPL`.
* **Приёмка:** при `MP_VITALS_IMPL=new` — те же строки лога и те же байты пакетов, что при
  `legacy`; `check_artifacts.py` видит только `KERNEL32`.
* **Откат:** `MP_VITALS_IMPL=legacy` (или revert коммита).

### E2. Интерфейс хоста

* Все обращения к codelib — через один `struct MpHost` (указатели на функции + адреса
  глобалов + пробы памяти). Никаких прямых `*(u32*)0x...` в бизнес-логике.
* Появляется **подставной хост** для тестов: фальшивая память игры, фальшивый лог,
  фальшивый отправщик.
* **Приёмка:** поведение не изменилось; новые юнит-тесты гоняют Vitals-логику без игры.
* **Откат:** revert; старая реализация не тронута.

### E3. Профиль как данные + внятный отказ

* RVA/сигнатуры — в одном месте, с проверкой каждой сигнатуры **до** установки хука.
* При несовпадении пишется одна строка с причиной (`profile: signature X mismatch at ...`)
  и DLL не вмешивается.
* **Приёмка:** подмена одного байта в копии codelib → DLL не грузится в хуки и пишет
  причину; игра работает штатно.
* **Откат:** revert (профиль всё ещё жёстко привязан к `485b6556…`).

### E4. Сетевой канал Vitals

* `0x34`/`0x35`: epoch, seq, окно повторов (400 мс, ≤12), дедупликация, mailbox.
* Тесты: потеря, дубликат, переупорядочивание, смена peer, реконнект.
* **Приёмка:** при тех же условиях — тот же объём трафика и те же применения, что в legacy.
* **Откат:** `MP_VITALS_IMPL=legacy`.

### E5. Монотонное состояние

* Солдат: своя health `+0x7c8`, health записи `+0x60`, смерть `< 0.5`; отряд/техника:
  флаги `+0xd07…+0xd10` без `+0xd0d`.
* Тесты монотонности: никакая последовательность пакетов не поднимает здоровье и не
  оживляет юнита.
* **Приёмка:** бой с расхождением (убит на одной стороне) → одинаковый итог; логи
  `dead here`/`still apart` совпадают с legacy.
* **Откат:** `MP_VITALS=1` (только лог) или `MP_VITALS_IMPL=legacy`.

### E6. Статистика боя

* Точная health у мёртвых, общий seed генератора `+0x130` перед подсчётом потерь,
  финальный скан перед статистикой.
* **Приёмка:** одинаковые потери и одинаковый seed в логах обоих ПК; мораль на карте
  считается одинаково.
* **Откат:** `MP_STATS=0` (существующий выключатель).

### E7. Guard'ы `basic_render` — последними

* Кэш transform-слотов, геометрия треугольника, invalid child. Три части раздельно:
  E7a кэш, E7b геометрия, E7c invalid child — каждая со своим выключателем.
* **Приёмка:** воспроизведение исходных дамповых условий (или эквивалентная нагрузка) —
  падения нет, guard срабатывает, лог содержит подтверждающую строку; обычный бой
  не деградирует по FPS.
* **Откат:** `MP_RENDER_GUARD=0` (существующий) + `MP_VITALS_IMPL=legacy`.

### E8. Завершение

* `legacy`-ветка удаляется, `MP_VITALS_IMPL` становится no-op, документация и
  `README_VITALS.txt` обновляются, хеши — в `BUILD_AND_VALIDATION.md`.
* **Приёмка:** полный набор S1–S7 зелёный.
* **Откат:** тег `v1.0.1`.

## 5. Порядок и ожидаемая стоимость

| Этап | Риск | Зачем он нужен |
|---|---|---|
| E0–E1 | низкий | структура без изменения поведения |
| E2–E3 | низкий | тестируемость и понятный отказ вместо «тихо не включилось» |
| E4–E5 | средний | сердце Vitals: расхождения здоровья и смерти |
| E6 | средний | итог боя и мораль на карте |
| E7 | **высокий** | падения `basic_render`; делаем последним, по частям, с выключателями |

Практическое правило: E1–E3 можно делать между прогонами; E4–E7 — только когда есть
свежий baseline и время на откат.

## 6. Что в этом плане не делается

* Не переписываем сетевой протокол и не меняем `k_version` — иначе ломается совместимость
  наших же сборок между собой.
* Не переносим v20-код в исходник: его у нас нет.
* Не пытаемся «убрать DLL» и встроить Vitals в codelib.
* Не трогаем карту операции: она заморожена до отдельного решения (см.
  `TACTICAL_OPERATION_STATE_POLICY_2026-10-25.md`).
