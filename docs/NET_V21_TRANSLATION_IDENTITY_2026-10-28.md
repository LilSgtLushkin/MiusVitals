# Исследование идентичности описаний, protocol 17 — 28.10.2026

## Состояние

Исследование продолжено по выбору пользователя, без запроса новых логов и без изменения политики
`match()`, формата protocol 17 или игрового поведения. Релиз отложен. Ниже отдельно указано,
что наблюдалось в старом игровом логе, что следует из машинного кода присланной сборки и что
проверено только на синтетических данных. Эти результаты не подтверждают 100% корректность боя.

## 1. Что уже есть в присланном логе 1.0.5

В `basic_network_tacgame_29980.log` из ранее присланного архива
`logs_20261028_020626_868_2c354ec2.7z.txt` есть одна сводка exchange:

| Показатель описаний | Количество | Доля из 4 229 |
| --- | ---: | ---: |
| Всего получено | 4 229 | 100% |
| Уникальный непустой 32-битный отпечаток по обе стороны («якорь») | 676 | 15,98% |
| Подставлено по позиции рядом с якорем | 3 553 | 84,02% |
| Из позиционных — отпечатки также совпали | 258 | 6,10% |
| Из позиционных — отпечатки различались | 3 295 | 77,91% |
| Не размещено | 0 | 0% |

Из всех 4 229 записей 4 225 получили тот же числовой ID и четыре — другой. Строка о совпадении
номера или отпечатка **не доказывает**, что указатели действительно означают одно и то же; в
логе нет исходных таблиц, названий и эталонных пар. Строка с теми же числами также есть в
`net_v21_tacgame.log`; её нельзя считать вторым независимым боем.

В этом же `basic_network_tacgame_29980.log` 70 пятесекундных сводок старого `shots` суммарно
сообщают о 1 593 локальных отправленных выстрелах, 1 875 полученных и вызванных локально,
3 090 подавленных локальных выстрелах чужих юнитов и нуле отказов по тогдашней проверке. Это
**счётчики модуля**, а не подтверждение того, что каждый снаряд был правильным, попал или
совпал с результатом второго игрока. Записей с номерами конкретных боеприпасов здесь нет.

Сопоставление относится к реальному Steam-прогону **1.0.5/protocol 14**, не к текущему
protocol 17. Однако исследованный `xlate.cpp` в [слитом коммите 1.0.5](https://github.com/LilSgtLushkin/MiusVitals/blob/fac71bcc8ce09c6f0545b6d4afda66639a13e81a/development/net-v21/src/xlate.cpp)
имеет SHA-256 `1594f9f81df5fcb7e98d432b307d3a7c3e16d1d9f9fa3e73b659e910b3111bc4`;
`fingerprint()` побайтно совпадает с текущим, а `match()` отличается только удалением
тавтологического условия `&& (pass || true)`. Поэтому сводка характеризует ту же эвристику,
хотя и не доказывает поведение новой сборки. Переход только на якоря исключил бы в этой
конкретной таблице 84% записей; какая часть из них участвует именно в выстрелах, неизвестно.

## 2. Идентичность в присланных PE-файлах

Адреса ниже относятся **только** к присланным образам `development/game-build-3598-1/x64/`:
`base_shell.codelib` SHA-256 `9606f69c38f997b7ae24a7152055f2bf612d5a38080d1e92be9c8bf0be7747e2`,
`adv_game.codelib` — `8f53c9018e7fc30a7e08daa16be5952a6aaec115412fa48245c2ee13046d1975`,
`basic_physic.codelib` — `a51aa13d94a89d776e12434a613b7bfa606525e50e473be8254b70995d98aa04`.
Статическая проверка адресов не устанавливает безопасность вызова игровых функций.

### Регистрация номеров

У `i_objman` в `base_shell` слоты 55/56/57 ведут на `+0x12280/+0x12120/+0x121d0`.
Последние два ищут соответственно номер по указателю и указатель по номеру: векторы по
`+0x1760/+0x176c` и `+0x1748/+0x1754`. При обычной регистрации первый метод ищет уже
зарегистрированный указатель; для нового использует номер из `+0x1778` и увеличивает его.
Это объясняет зависимость ID от порядка регистрации, но не доказывает, что этот порядок
совпадает в двух процессах, что счётчик никогда не сбрасывается, или что доступ к нему
межпоточно безопасен. `match()` не использует один локальный индекс дважды: это отдельно
зафиксировано тестом с отсутствующей записью.

### Имена оружия и снарядов

В `adv_game` конструктор создаёт `i_weapons` с таблицей виртуальных функций `+0x12e180`.
Код загрузки резервирует массив оружия по `i_weapons+0xf0` с шагом `0x130` и массив снарядов
по `+0x108` с шагом `0x170`; элементы обоих массивов затем регистрируются у object manager.
Индексы имён расположены отдельно по `+0x120` и `+0x138`: каждая строка занимает `0x44` байта,
содержит длину и текст, а по `+0x40` — индекс элемента соответствующего массива. Код поиска
ограничивает имя 61 байтом. Виртуальные слоты 8/9 проверяют наличие имени, 3/4 получают
указатель по имени, слот 7 перечисляет указатели на inline-имена оружия по `weapon+0x42`.

Это перспективные признаки **для этих двух категорий**, а не готовый универсальный ключ:

- разные полные имена с одинаковыми первыми 61 байтами не различаются этим поиском;
- в записи оружия есть и другая строка по `+0x80`, которую код использует при поиске оружия
  для снаряда. Загрузчик создаёт пронумерованные имена `%s%u` и копирует запись из того же
  источника; указатель на строку `+0x80` при этом может повторяться. Само имя варианта в
  отдельной области по `+0x42` не следует путать с этой строкой;
- `match()` хеширует только первые `0x60` байт, то есть в этот диапазон помещаются лишь первые
  30 байт inline-имени, начинающегося по `+0x42`;
- одинаковое имя не доказывает одинаковый набор модов, конфигурацию или прочие поля, а
  применимость этих массивов ко **всем** указателям в реальных выстрелах пока не установлена;
- для `desc3` и остальных типов описаний универсального имени не найдено. Игровые `.cfgpack`
  и снимки таблиц памяти в 19 присланных файлах отсутствуют.

Не следует вызывать слоты 3/4 с непроверенным именем: если поиск не нашёл его, машинный код
переходит к чтению строки с индексом `count` без видимой проверки результата. В эмуляторе
синтетическая таблица, заканчивающаяся у границы страницы, при таком вызове даёт ошибку чтения;
реальное выделение может иметь дополнительную память, и реальный вылет этим не доказан.
Слоты 8/9 в той же фикстуре корректно сообщают об отсутствии имени. Без проверки сборки, ABI,
времени жизни и потоков эти методы в производственный модуль **не подключены**.

### Один путь от имени до записи запуска

Для одного конкретного пути удалось связать эти массивы с реальным машинным кодом запуска, а
не только предположить такую связь:

1. Конструктор `i_divisions` регистрирует обработчики `generate` и `ctrl_tick` и зависимости
   `i_weapons` по `+0x118` и `i_shellphys` по `+0x120`. `generate` через `+0x81470` и
   `+0x82a30` попадает в загрузчик `+0x82bf0`.
2. Загрузчик создаёт массив записей по `i_divisions+0x3e0` с шагом `0xa0`. В одной записи
   результат поиска оружия по имени записывается по `+0x20`, снаряды по именам — по
   `+0x28` и в последующие слоты с шагом 8. Используются слоты 3/4 `i_weapons`.
3. `ctrl_tick` через `+0x81500/+0x85b00` на одном из путей вызывает `+0x42d40`. Тот
   выбирает запись из массива `+0x3e0`, берёт указатель снаряда из `+0x28 + индекс*8`
   и указатель оружия из `+0x20` и кладёт их соответственно в launch-record по `+0x38`
   и `+0x40`; затем вызывает слот 3 зависимости `i_shellphys`.

Дополнительный offline-тест исполняет **отдельные связанные фрагменты** этих реальных
инструкций, включая сами функции поиска имён, на синтетических объектах. Он проверяет
ненулевые индексы записи и снаряда и состав сформированной записи перед вызовом. Это не
запуск всей игровой функции: ветки и данные фикстуры заданы тестом. Связь установлена лишь
для описанного пути; она не доказывает, что все выстрелы, `desc3`, игровые конфигурации,
времена жизни или потоки подчиняются той же схеме, и не устанавливает идентичность имён
между игроками.

### Изменяемые байты отпечатка и слабая проверка выстрела

В `adv_game+0x6cb20` слот 10 `i_weapons` печатает `Velocity correction to ... by temp ... C`
и для некоторых записей снарядов пересчитывает 16 байт по `shell+0x20` из значений по
`+0x30`; условие использует flags по `+0xc0`. Указанные `+0x20..+0x2f` входят в
`fingerprint()` и могут меняться **без регистрации нового описания**. Эмуляция реального кода
на синтетических записях дала коэффициент 1,0 при 293 K и примерно 1,1 при 353 K; это проверка
инструкций, а не наблюдение температур в реальном бою. Нельзя утверждать, что именно этот
механизм вызвал различия отпечатков в логе 1.0.5.

В текущем `send_changed_tables()` при одинаковом количестве описаний и объектов проверка
содержимого вообще пропускается. Тест настоящего `xlate.cpp` отдельно подтверждает: изменение
синтетических байтов `+0x20` меняет fingerprint, но само по себе не ставит таблицу на
повторную отправку. Это может оставить старый отпечаток у peer; само по себе ещё не доказывает
неверный игровой перевод. Безопасность и нагрузка безусловного пересчёта/повторной отправки,
а также согласование поколений таблиц и выстрелов не доказаны; такой патч не внесён.

В `basic_physic+0x185c8/+0x185d4` launch получает weapon и ammo из записи по `+0x40/+0x38`.
Далее он использует, среди прочего, `weapon+0x88/+0x90` и `ammo+0xc0`; они находятся за
пределами первых `0x60` и не входят в проверку выстрела. Проверяемый `ammo+0xc4` сравнивается
с типовыми кодами вроде `HEAT` и `FRAG`, то есть это не доказанный уникальный идентификатор.
Текущий wire несёт ещё только два первых числа ammo. В синтетической интеграционной фикстуре
уникальные совпадения отпечатков и эта короткая проверка выбирают заведомо неверные fixture
ammo/weapon, после чего настоящий `shots.cpp` вызывает поддельный launch и отправляет ACK.
Это демонстрация возможности, **не доказательство**, что такие пары встретились в игре.

## 3. Что делать дальше и чего нельзя обещать

Возможный будущий путь — передавать или согласовывать ограниченные имена из `i_weapons` с
разделением категорий, проверкой уникальности, поддержкой старого peer и явным отказом при
несовпадении. Для этого ещё нужно доказать границы применимости, обработать 61-байтное
усечение, одинаковые имена с разными данными, отсутствие имени, `desc3`, обновление поколений,
потоки и нагрузку. Старый приёмник 1.0.7 сам не станет безопаснее. Дополнительные метаданные в
записи или новый тип события были бы изменением **семантики** wire, даже если размер структуры
и номер версии остались бы прежними; их совместимость нельзя объявлять заранее. Новый
capability bit, отдельный поток или SACK здесь не реализованы.

Для оценки совместимости добавлен отдельный **синтетический** эксперимент: тестовый отправитель
необычно заполняет 40 байт пяти обнуляемых указателей launch-record и байт `pad`; остальные
поля сохраняются в прежнем размере. Приёмники из исходника 1.0.7 и текущей ветки в фикстуре
восстанавливают все пять ненулевых синтетических указателей перед вызовом поддельного launch,
передают отдельный `obj5`, сохраняют контрольный байт вне указателей и принимают ACK. Проверены
обе стороны как отправители и приёмники. Это
лишь наблюдение за конкретным no-game сценарием, **не** реализация формата, передачи имён или
согласования возможностей: обычный production-отправитель по-прежнему обнуляет указатели,
старый приёмник по-прежнему может воспроизвести неправильную пару, а безопасность для других
сценариев, проверка данных, поколения, все версии и игра не доказаны. Одного этого эксперимента
недостаточно для разрешения менять семантику protocol 17.

Без этих доказательств ни строгий отказ по всем позиционным парам, ни переключение на новый
ключ не выбраны автоматически. Уже внесённый 10-секундный терминальный отказ может потерять
событие и не устраняет риск неправильной пары, которую `match()` всё-таки нашёл.

## 4. Воспроизводимые no-game проверки

```sh
python -m pip install capstone unicorn==2.1.4
python development/game-build-3598-1/manifest.py --verify
python development/net-v21/tools/xlate_identity_pe_selftest.py
python development/net-v21/tools/xlate_identity_emulation_selftest.py
```

Первая проверка сравнивает инструкции и SHA трёх PE, вторая исполняет ограниченные фрагменты
оригинального x64-кода в Unicorn на выдуманных объектах и индексах; `memcpy` и игровой логгер
заменены заглушками. Ни игра, ни Steam, ни настоящие игровые данные не запускаются. Добавлены
также тесты настоящих `xlate.cpp` и `shots.cpp`: совпадающие/недостающие fingerprint,
синтетический ошибочный unique anchor и изменение fingerprint при неизменных счётчиках.

Локально под ASan/UBSan `xlate_selftest` выполнил 27 проверок, а интеграция `shots`/`xlate` —
15, без ошибок. Zig скомпоновал оба теста в Windows PE; исполнять их локально не удалось.
На Windows/MSVC прошёл [CI 40720063193](https://github.com/LilSgtLushkin/MiusVitals/actions/runs/40720063193)
для коммита `f526509`: он собрал и исполнил оба C++ теста, проверил восемь пар совместимости,
прежнюю версию обеих offline-проверок и одношаговый временный установщик. Дополненная цепочкой
версия обеих offline-проверок также прошла Windows CI
[40721443834](https://github.com/LilSgtLushkin/MiusVitals/actions/runs/40721443834) на коммите
`a185a0f` и локально даёт 7/7 в статической проверке и 7/7 в Unicorn. Расширенная матрица из
12 mixed-version процессов проходит локально под ASan/UBSan. Ни один из этих прогонов не
запускает настоящую игру или Steam.
